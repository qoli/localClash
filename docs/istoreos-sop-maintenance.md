# 如何維護 iStoreOS 測試 SOP

日常維護以 [功能測試表](istoreos-test-features.md)為主；只在測試方法改變時調整
[功能驗收 SOP](istoreos-release-test-sop.md)，代理分工則集中在 [測試 skill](../.codex/skills/localclash-istoreos-test/SKILL.md)。

## 功能變更時

核對正式產品入口與實作，再更新受影響的功能列。一列代表完整產品能力，必須描述使用者
可觀察的不變量、獨立外部 oracle 及能力承諾包含的狀態轉移；CLI／MCP／LuCI 不因入口
重複列功能。維持 Core／LuCI 歸屬及 Mihomo 責任界線。新功能才新增穩定 ID；既有 Bug
可以加入專用回歸，但不得用該回歸取代完整能力契約。

## 測試完成時

更新真正執行的版本、核心、輸入等價類、狀態轉移、外部 oracle、結果與證據連結。
局部結果不擴大為整項通過，沿用不改成新版本 PASS。保留失敗及後續回驗；後來觀察到的
同功能失敗要撤回或取代舊 PASS，不能只追加一條新版本紀錄而保留錯誤結論。
匯入舊證據先核對入口、版本及斷言；缺資料標示待核對，不據此要求全表重跑。

## 方法需要調整時

先判斷內容屬於功能契約、共用操作流程還是代理分工，只修改對應文件。測試設計按不變量、
狀態轉移及等價類建立，不靠窮舉環境或累積已知 Bug 清單。實際結果放本輪報告，修訂歷史由 Git 保存。
主機端 mock／fake／stub 只能屬於開發檢查；不得寫入 QEMU 驗收證據、功能表結果或發布 PASS。
避免把同一規則複製到 README、發布文件或其他倉庫，使用連結指向其維護位置。

完成後核對引用與錨點、功能 ID 及歷史證據是否保持正確。若移動或刪除文件，同步修正
Core 與 LuCI 的呼叫入口；文件整理本身不新增產品實測紀錄。
