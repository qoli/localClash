# 如何維護 iStoreOS 測試 SOP

日常維護以 [功能測試表](istoreos-test-features.md)為主；只在測試方法改變時調整
[簡要 SOP](istoreos-release-test-sop.md)，代理分工則集中在 [測試 skill](../.codex/skills/localclash-istoreos-test/SKILL.md)。

## 功能變更時

核對正式產品入口與實作，再更新受影響的功能列。一列代表完整產品能力，新增／刪除等操作
放在該列驗證內容內，CLI／MCP／LuCI 不重複列功能。維持 Core／LuCI 歸屬及 Mihomo 責任界線。
新功能才新增穩定 ID；既有功能修 Bug 通常只需補清楚正常操作的預期。

## 測試完成時

更新真正執行的版本、核心、覆蓋範圍、結果與證據連結。局部結果不擴大為整項通過，
沿用不改成新版本 PASS。保留失敗及後續回驗，未執行項維持原歷史。
匯入舊證據先核對入口、版本及斷言；缺資料標示待核對，不據此要求全表重跑。

## 方法需要調整時

先判斷內容屬於功能定義、共用操作流程還是代理分工，只修改對應文件。
不用每次 Bug 或發版新增規則、案例文件或維護日誌；實際結果放本輪報告，修訂歷史由 Git 保存。
避免把同一規則複製到 README、發布文件或其他倉庫，使用連結指向其維護位置。

完成後核對引用與錨點、功能 ID 及歷史證據是否保持正確。若移動或刪除文件，同步修正
Core 與 LuCI 的呼叫入口；文件整理本身不新增產品實測紀錄。
