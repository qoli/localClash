# iStoreOS 功能追蹤與按影響選測 SOP

狀態：現行規範，2026-09-08 重寫。取代以 G00–G99 全套流程作每輪起點的規則。
使用者決定：先建立功能表；每個功能追蹤最後實際測試版本；每次變更只測受影響項。

這是 localClash Core 與 localclash-luci 共用的唯一選測、證據沿用及發版判定規範。
**不同功能最後測試於不同版本是正常狀態。發版不等於全部功能重跑。**

| 入口 | 責任 |
| --- | --- |
| [功能追蹤表](istoreos-test-features.md) | 長期保存每個功能／核心的最後實測版本、結果與證據 |

| [案例參考](istoreos-test-cases.md) | 按需讀取操作、基線及斷言；舊案例編號只供對照 |

## 1. 任務與範圍

| task_mode | 交付 | 不自動要求 |
| --- | --- | --- |
| diagnosis | 症狀、實際版本、證據、已知原因或明確缺口 | 改碼、產品測試全表、發版 |
| targeted_repair | 修復、選定功能重驗、相關帳本與問題回寫 | 無關功能補測、G99 |
| release_acceptance | 本候選影響審查、必要重驗、未受影響證據沿用與 G99 | 全部功能在本版重新執行 |
| full_baseline | 首次建立完整功能基線、明確要求全測，或有證據顯示影響遍及全表 | 每次改版自動重新建立 |

先記使用者目標、任務範圍、Core／LuCI 的比較基準及候選 commit、dirty 差異與授權。
一般發版使用 release_acceptance；full_baseline 必須列明觸發原因及展開範圍。
單項定位／修復不因功能表仍有待核對項而變成 full_baseline。

只操作本輪指定的可拋棄 x86_64 iStoreOS QEMU；它仍是產品功能驗收環境。
單元、契約、語法與封裝檢查依 owning repo 要求執行，不能代替所選 QEMU 斷言。
ARM64 封裝證據不冒充 ARM64 runtime 或實機驗收；Docker 可作建置工具，不作功能驗收。
不改生產路由器或宿主預設路由／DNS。Core 不執行 fw4/nft/uci/ip rule；接管由 LuCI 負責。
訂閱 URL、憑證及完整配置只存受限本機證據；版控只收脫敏摘要與證據索引。
本 SOP 不授權推送、tag、Release 或公告，這些仍依使用者的發布授權。

## 2. 功能表的維護方式

一列代表能獨立選測及判定結果的功能或必要子功能，使用穩定 ID。
取證層、工具啟動步驟及每個按鈕點擊不另冒充產品功能。複合功能只驗部分時，
記錄具體子項；不能用部分 PASS 把整個功能標成 PASS。新增／移除正式功能時更新功能表。

每個功能至少保存：

- 名稱、斷言範圍、正式入口／案例參考及適用核心。
- 最後**實際執行**的 Core／LuCI 版本；未發布候選用 commit／patch 身分。
- 最近實測結果、具體覆蓋範圍及證據。只有建置身分／環境準備時不能填成實測版本。
- 證據內的產物 SHA、實際載入身分、相關 Mihomo／模型身分、環境、attempt 與時間。

Meta／Smart 的結果分別追蹤；shared 僅用於不依賴活躍核心的安裝／靜態斷言。
共用實作修改需審查雙核心受影響路徑，不把一個核心的 PASS 複製到另一個。

本輪沿用不更新「最後實測版本」。新測試 FAIL 要記最近失敗並保留舊 PASS 連結；
若只有前置 ERROR 或 NOT_RUN，保留最後產品實測，另外記本輪未完成原因。
歷史欄位「待核對」代表證據匯入尚未完成，不等於功能從未測試或必須立刻重跑。
先找原紀錄核對；只能按實際已驗範圍匯入，不根據舊總報告的一句 PASS 擴大聲稱。

## 3. 每輪如何選測

1. 讀功能表與本輪差異，按「變更 → 入口／共用契約 → 受影響功能 ID」建立對照。
   不能只看檔名、版本號或最後一個 commit。只改文件就選文件／skill 行為與引用檢查。
2. 交獨立 Reviewer 判定直接重測、必要回歸、沿用與前置依賴。每項寫理由及斷言。
   訂閱處理改動需審查保存／刷新，以及真正受影響的初始化／更新路徑；不能因此
   自動加入重置、全部 DNS、每個舊版或全部 K/R/X。
3. 對需要沿用的功能，比較**該功能最後有效證據的版本至本候選**，包含累積程式、
   依賴、配置及環境差異；不能只比較本次改動而漏掉中間版本。確認入口／斷言仍成立。
4. 缺證據先補讀；證據失效或仍不足時，只新增真正缺少的功能／核心／子斷言。
   「未知」不能直接推成全部功能重跑；改動共用檔案也不是全測理由。
5. 鎖定本輪計畫，再依依賴執行。新發現若改變選測結論，保留原嘗試並交 Reviewer
   補審具體受影響項；沒有相關變化就不重新建立整份計畫。

追蹤鍵是「功能 ID＋核心＋必要 variant／子斷言」。功能表定義適用範圍，
本輪只重驗其中受影響部分，其餘沿用各自有效證據；不能臨時縮小功能定義來湊整列 PASS。
純欄位、文字、引用改動可用 DOC 類本輪 ID，不為它們新增永久產品功能。

本輪計畫獨立於長期功能表，可以是一份簡短 Markdown：

| feature_id／核心／子項 | 處置 | 影響或沿用理由 | depends_on／所需能力 | 實測或沿用證據 | 本輪結果 |
| --- | --- | --- | --- | --- | --- |
| 從功能表選定的 ID | test / reuse / investigate / out_of_scope / not_applicable | 差異與契約依據 | 具體能力，無則空 | attempt／原版本證據 | 待執行或結果 |

這是欄位格式，不是實測資料。修復計畫只列所選功能與必要的排除說明；發版計畫對
支援功能給出 test／reuse／not_applicable 處置，可用明確 ID 清單成組引用未受影響項。
out_of_scope 用於單項任務，不用來隱藏一般發版的支援功能缺口。N/A 必須有正式能力／
環境條件證據，不因時間不足、失敗或難測而使用。

一般發版仍要求所需功能有適用證據，可以是本輪實測或經核對的歷史證據。
首次完全沒有可用基線時建立 full_baseline；少量待核對／失效項只補其缺口。
既有歷史未整理不作全表重測理由，也不能讓無證據功能自動算作 reuse。
文件或規則重寫本身不更改任何既有產品報告的放行結論。

## 4. 前置能力與真正依賴

先驗所選功能需要的測試資源，再操作產品。按需核對可啟動的 overlay、guest 身分、
登入／UI／RPC、候選來源及資產；涉及 LAN 時驗 client gateway、受控端點與相關協定。
網路 fixture 在產品接管前就無法提供預期回應，應記環境 ERROR，不能推論產品失敗。
換拓撲或克隆後核對所需能力；工具腳本啟動成功不是環境已就緒。

使用現有 [VM 腳本](../scripts/istoreos-test-env.sh)；它只管理 VM，不是全測 runner，
也不自動建立 LAN client、受控端點或候選來源。需要這些能力時按案例參考準備。
只複製已停止的 overlay，隔離端口、磁碟及故障注入；結束後核對並停止本輪程序，保留證據。

依賴指向具體**能力與身分**，不指向「前面所有章節都 PASS」。例如：

- B／Meta 需要合格的候選 Meta 運行基線，不依賴 B／Smart。
- C 需要所選舊版 S1 與可用候選安裝來源；D/E 需要該遷移路徑所需的舊狀態。
- K/F 中某功能已有所需基線，就不因其他 A–E 分支尚未完成而禁止執行。
- 同一共享資源失敗可阻擋所有真正依賴者；資源獨立的分支可以繼續，即使順序執行。

正常初始化、已知故障狀態、正式恢復後狀態分別保留身分與來源。舊版初始化 FAIL
不改寫；候選可從有來源的舊故障狀態測支援的恢復／遷移，但不能冒稱正常升級 PASS。
缺少正常 S2 時先找合格歷史快照、核對實際支援遷移範圍，明列缺的路徑；
不要求先修好舊版才能測新候選，也不無據豁免候選承諾的正常升級能力。

<a id="results"></a>
## 5. 結果、證據與異常

| 層次 | 值 | 意義 |
| --- | --- | --- |
| 產品斷言 | PASS / FAIL | 已實際執行；預期拒絕且保護正確可以 PASS |
| 執行／取證 | ERROR / NOT_RUN | 環境、工具或取證不可用；或尚未執行，附具體原因／依賴 |
| 證據適用性 | valid / stale / unknown | 能否支持本候選，與歷史執行結果分開 |
| 本輪處置 | test / reuse / investigate / out_of_scope / not_applicable | 計畫中的選擇；不是實測結果 |
| 發版評估 | PASS / BLOCKED / not-assessed | G99 結論；不當作每個未執行案例的結果 |

每次實測保留不可覆寫的 attempt：功能 ID／核心／子項、原定斷言、候選與實際身分、
基線、正式操作入口與 task、前後狀態、結果、時間與證據。HTTP 200、task_status ok、
PID 或 controller ready 單獨都不證明功能成功；按所選功能取得材料、runtime、接管、
LAN 回應與路徑證據。UI 功能必須驗真正 UI，純 RPC 證據不能冒充點擊與頁面恢復。

受控功能與公共網路品質分列。必要功能違反契約記 FAIL，不必等根因定位；
外網逾時不自動稱 Core／LuCI／Mihomo 缺陷，也不要求每筆都有修復 commit。
工具無法判讀記 ERROR；正常產品操作返回失敗記 FAIL，另外記歸屬信心。

案例執行前指定證據來源、觀測時間窗與 task/request 關聯。保留該集合內的非預期
錯誤、重試及 warning，關聯異常 ID；已確認產品缺陷再加問題 ID。預期拒絕／內建
重試按事前契約解讀。對帳檢查所選集合，缺少必要來源就是缺證據，不能當作零錯誤；
不要求替整台 VM 的所有背景訊息找根因才能結案。

首次操作 FAIL 不因重試／補救成功而消失。負向案例按計畫恢復；額外診斷不得冒稱
正常路徑。新證據採納時連到取代的舊結論，保留原檔；未解失敗不能由較舊 PASS 遮蔽。

<a id="writeback"></a>
## 6. 收尾與回寫

實測後更新功能表的相應功能／核心／子項、最後實測版本、結果與證據；未執行及
沿用的欄位保持原版本。本輪紀錄另寫採納哪個 attempt、沿用依據、未完成項及原因。
版本標籤不是源碼證明；模型／核心變更按相關功能分開身分，不混成同一批實測。

只回寫受影響功能、既有問題與發布摘要。不為單項修復建立空白全表，不為每個 Bug
另加永久 SOP 條款。已有現行驗收報告時，連到新證據及被取代結論；舊原始報告保留。
本機原始證據預設放 `.runtime/istoreos-acceptance/<run-id>/`，run-id 含日期與候選識別。
功能表的本機證據連結在其他工作站不可讀時，需取得脫敏證據包後核對，不能當作可用 PASS。

完成條件：本任務範圍已處理、所選斷言有結果、異常已記錄、功能表及受影響結論已回寫。
定位按診斷交付完成，並不要求故障消失。測試工作可交付 FAIL／ERROR 與明確缺口；
修復宣稱「已驗證」則需要相關必要斷言通過。未執行的無關功能不妨礙單項任務結案。

<a id="g99"></a>
## 7. G99：本候選的覆蓋與發版評估

G99 是收尾評估，不是另一輪測試。release_acceptance／full_baseline 才作發版結論；
定位與針對性修復記 not-assessed，不覆寫既有發布判定。

本候選功能覆蓋成立，須同時滿足：

1. 每個支援範圍內功能／核心／必要子項有處置；新測通過，或歷史證據經核對仍適用。
   完整展開範圍來自功能表及本輪選測計畫，不臨時以「所有舊章節」追加關卡。
2. 所選必要斷言沒有未解除 FAIL、ERROR、NOT_RUN 或 unknown/stale 證據缺口。
   非適用功能附條件證據；已觀察的未解功能故障不能以 reuse/out_of_scope 避開。
3. 最新候選身分、原始實測版本與沿用範圍可追溯；修復後的新證據明確取代舊阻擋。
4. 已執行項及範圍內異常有紀錄，功能表與本輪摘要一致。

摘要至少列：候選配對、review ID、test/reuse/不適用功能清單、實測結果、
仍缺的必要斷言、非阻擋外部觀察、證據入口、結論與審核者。
不同功能最後測試版本不一致不構成阻擋。缺哪個功能就指出哪個缺口，不倒退成全表重跑。

產品覆蓋成立後仍需核對發布資產／tag 身分及既有代理執行規範，再由發布責任人放行。
現行 CI 不執行 QEMU 或自動核驗此表，G99 仍是人工審核，不能宣稱已建成自動門禁。
若公開產物重建，按 release runbook 核對受測內容及 SHA；不一致先調查受影響證據，
不盲目沿用或繼續廣播。候選資產直接提升尚非現有能力。

## 8. 代理與規範遷移

Pi CLI／Kimi Reviewer 與 Luna High 分工維持既有要求，細節在
[代理執行規範](istoreos-test-agent-workflow.md)。Reviewer 依本 SOP 的功能／差異證據
作選測；不能因任務叫「發版」或功能最後測試版本較舊，就要求全表重跑。

歷史 G00–G99、BLOCKED、核心彙總與各 attempt 都保留作歷史證據。功能表匯入逐項
核對版本、入口、斷言及原始證據，不能將過去整輪 BLOCKED 解讀成所有功能都失敗，
也不將新規範自動套成過去某版本已 PASS。規範重寫本身不代表已執行產品驗收或取得公開發布授權。
